# Refiner 双文本来源原型与拆分顺序修复

2026-10-04。本轮新增 API、模型推理、训练、权重、密钥及金标读取均为 0。[聚合结果](results/refiner_dual_text_20261004.json)、[原型](../../SLAC/refiner/pipeline/assemble/source_atomizer.py)和[固定样本检查](probe_refiner_dual_text.py)保留实现及来源绑定。

**固定两文档的 83 个单元全部通过原文来源与重建检查，包括上一阶段缺少精确原文对应的四个单元；模型输入仍与缓存的 251 个 atom 逐项相同。** 这是可接入的双文本表示原型，默认 pipeline 尚未调用它，没有新增模型质量结果。

## 两份文本如何对应

[上一阶段](REFINER_SOURCE_BUDGET_RESULTS_20261004.md)发现，规范化后的四个 atom 已不是原文的精确子串。直接事后匹配无法为它们提供符合现有 source-mode projector 要求的坐标。本原型在执行字符替换、空白折叠、句切分、长切分及短片段合并时携带来源，而不是在得到模型文本后再猜原文位置。

`trace_atomize_unit_text(source_text, cfg)` 返回 `AtomizationTrace`：

- `model_atoms`：模型看到的规范化 atom。每次调用都要求它与修复后的生产 `atomize_unit_text` 逐项一致，不一致就拒绝给出通过结果。
- 每个 atom 的 `model_char_origins`：逐模型字符的 Python 原文字符区间。CRLF／空白折叠可以是多对一；真实合并操作插入的模型空格用 `None` 表示，不能冒充来自某个原文字符。
- 每个 atom 的 `source_span/source_text`：独立的原文渲染分区。分区连续、无重叠，保留全部首尾和中间原文字符；不声称它与 `model_text` 字节相等。

原型直接复用生产的切点、标题判断、近似长度和 CJK 等纯决策函数；少量控制流程携带来源信息，并在末尾强制核对生产输出。原文所有非空白字符都必须被字符来源覆盖，来源不能逆序或重叠。空白-only 输入完整保留为 `trivia_only`，不制造虚假 atom，也不宣称非空 source 可以作为零 atom 的 projector 输入。

`operations` 记录中也包括被评估过的候选操作；最终字符来源和渲染分区才是返回 atom 的对应依据。实现没有改动默认推理入口、旧 exporter 或 JEV 判断契约。

## 先修复了一个真实顺序错误

在实现来源跟踪时，合成反例暴露出生产长文本拆分的 FIFO 遍历问题：左侧仍需递归拆分时，已经足够短的右侧会先输出。

例如输入 `ABCDEFGH: IJ`，字符上限 5、软下限 0，旧公共 atomizer 输出 `['IJ', 'ABCD', 'EFGH:']`，顺序与原文相反。默认 480 字符配置也可复现：`'A' * 480 + ': END'` 会先输出右侧的 `END`，随后短片段合并仍保留错误顺序。

[最小修复](../../SLAC/refiner/pipeline/assemble/build_refiner_input.py)将遍历改为左到右的 DFS，保留原切点、规范化和合并规则。[7 项回归测试](../../tests/research/test_refiner_split_order.py)覆盖左长右短、镜像控制、无分隔符硬切分以及默认上限，检查内部拆分与公共 atomizer。旧源码字节和修复前见证均保留在私有产物中。

这个合成错误不等于既有研究样本已经受影响。后续固定样本检查确认：本次两文档的 251 个旧 atom 在修复后全部不变。对其他文档、历史训练数据或权重没有重新审计，也不扩大这个兼容性结论。

## 固定样本实测

在代码、协议、测试、输入和本地 tokenizer 的 hash 冻结后，只运行了一次原先两篇开发文档、83 单元的检查。沿用旧缓存，不重新读取上游语料或挑选新样本。每个单元都验证了字符替换的来源解释、原文顺序、非空白覆盖和完整渲染分区；失败也必须保留在分母中。

| 指标 | 文档 1 | 文档 2 | 合计 |
|---|---:|---:|---:|
| 输入／通过来源检查的单元 | 60/60 | 23/23 | 83/83 |
| 模型 atom | 177 | 74 | 251 |
| 模型 atom 列表与旧缓存完全相同的单元 | 60 | 23 | 83 |
| 上阶段无完整精确匹配、现通过双文本检查的单元 | 0 | 4 | 4 |
| 合并操作插入且明确标记 `None` 的模型空格 | 10 | 8 | 18 |
| 模型文本与原文渲染文本字节不同的 atom | 123 | 52 | 175 |
| 完整原文与旧 exporter 文本相同的单元 | 54 | 19 | 73 |

175 项 atom 字节差异包含原文间隔分配和规范化差异，不能解释为 175 处语义变化。18 个空格是模型合并操作的新增字符标记，也不代表原文相应位置一定没有空白。

真实 `projector.spans_to_units` 接收的是**原文渲染 atom 与对应原文分区**，分别按逐 atom 分区和整单元分区重建，83 项均逐字节恢复原文。模型 atom 单独保持原生产输入；没有把规范化模型文本伪装成原文切片。这里验证的是单元内桥接，没有执行整篇文档的 source-mode 预算投影或生产导出接线。

按完整原生单元重新计实际 BGE tokens（包含 special tokens、无截断），77 项与旧 exporter 相同，6 项各多 1 token，与前阶段保留空白的观察一致。四个补齐来源的单元没有额外 token 差。本轮未重新选择证据包、计算质量指标或宣称 API 缓存命中。

## 验证及接入边界

**48 项相关测试通过**：7 项拆分顺序回归、27 项[双文本合成测试](../../tests/research/test_source_atomizer.py)、14 项已有 seed 归属回归。合成测试包含全角／弯引号替换、CRLF 和多空白、Unicode 字符坐标、重复文本、前向／后向合并新增空格、CJK 合并、trivia、生产输出不一致时拒绝，以及真实 projector 接收渲染视图、拒绝将模型视图冒充原文的反例。

有界独立复核直接比较了旧缓存的 251 个模型 atom、保存的字符来源与原文切片，并用本地 tokenizer 对 92 种唯一字符串复算 83 单元两侧计数，全部通过；没有重新运行来源算法、builder、projector 或测试，也没有扩大语料范围。

默认生产流程只应用了拆分顺序修复；双文本原型仍是显式调用。下一步保持零 API，先在同两篇文档上验证从单元坐标到文档坐标的组合与间隔覆盖，再接入使用同一渲染文本的投影和导出。继续保留原 `b0`、同规则投影后的 `b0` 与模型边界的贡献区别，不把规则变化当成学习收益。

这些修复与来源契约使公平的后续框架实验更可执行，但本身不构成论文创新或 SLAC×JEV 效果证据。真实模型边界、JEV 新粒度判断以及质量收益仍待验证。
