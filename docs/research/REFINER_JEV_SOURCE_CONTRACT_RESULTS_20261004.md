# Refiner 新粒度的来源覆盖与 JEV 请求身份

2026-10-04。继续使用原来的两篇文档、83 个 native Unit、251 个 model atom，完成从原文导出块到现有离线 JEV 请求契约的可选适配。**251 个 leaf 中，221 个仅覆盖原生单元的一部分；56 个规则投影块中，23 个合并多个完整单元。** 来源归属不能据此转换成旧段落的支持标签或分数。

本轮验证 390 条覆盖记录与 139 对离线请求身份。请求使用一个明确的人工身份检查问题及 offline endpoint/model 名称，未读取真实问题、旧判断或金标，没有发送请求。API、模型推理、权重读取和训练均为 0。58 项新增测试通过。这仍是接口与可追溯性进展，没有新增 JEV 判断、RAG 质量或创新性结果。

## 接通的接口

新增 [`source_coverage.py`](../../SLAC/refiner/pipeline/assemble/source_coverage.py)，在已验证的不可变 `DocumentSourceView` 上建立 native 原文区间索引。`cover_atoms(start, end)` 返回原文区间交集，不进行文本搜索或模糊匹配。

- `full`：覆盖整个 native 原文字符区间。
- `partial`：只覆盖该区间的非空严格子集。
- `exact_native_unit_id`：仅一个完整单元、没有额外字符且原文区间完全一致。完整单元加换行不满足它。
- `gap_chars`：native 区间之外的空白。段内空白仍属于该单元；非空白缺口被拒绝，重复文本按身份和坐标区分。

新增 [`refiner_bridge.py`](../../SLAC/retrieval/decision/refiner_bridge.py)，核验选定 source-mode chunk 的文档、坐标系统、atom 数量、原文跨度及实际文本与 `view.render(...)` 相同，再生成不可变快照。若记录提供来源 SHA256，也必须匹配。它校验当前行与给定来源视图，不声称认证整个导出文件的历史身份。

快照的 `Unit.order` 使用 `atom_start`，保留共同 atom 基准上的来源顺序。同文档的多个快照必须具有相同原文版本、坐标系统、model atoms 与 atom 原文区间；可以使用不同 chunk 边界，也保留合法的区间重叠。现有 core 对重复 ID、相同来源起点、完整重复文本的拒绝规则保持不变。

请求构造复用已有 `conditional.build_request`、`FrozenRequest` 和缓存／响应校验，仅支持 `standalone` 与 `plain_conditional`；不自动构造关系，不添加网络客户端。来源 SHA、坐标、原文覆盖清单单独存入绑定 `request_key` 的 provenance receipt，模型输入仍是实际问题与完整可见文本。

## 固定样本覆盖结果

输入仅为已封印的两文档来源／映射文件和上一轮保存的 source export，按原顺序完整保留。没有重跑 Refiner builder、投影器、导出器或模型。原始 b0 块、规则投影块、leaf 各自独立分割完整文档；每一组都恰好覆盖全部 83 个 native 单元的原文字段字符一次，并保留 162 个单元间换行字符。

| 粒度 | 记录数 | 仅完整覆盖一个单元 | 完整覆盖多个单元 | 仅部分覆盖一个单元 | 与一个完整 native 单元文本精确一致 |
|---|---:|---:|---:|---:|---:|
| 原始 b0 chunk | 83 | 83 | 0 | 0 | 2 |
| 规则投影 chunk | 56 | 33 | 23 | 0 | 1 |
| source leaf | 251 | 30 | 0 | 221 | 0 |

两文档的 leaf 部分覆盖数分别为 155/177 与 66/74；规则投影的多单元块分别为 17/41 与 6/15。样本内没有混合完整／部分的 chunk，因为本次规则投影仅合并原始边界。混合覆盖已由合成例子验证，不能因这个自然样本没有出现而在接口中省略。

这里的 native 单元包含数据集原文字段，不能把所有单元都称作有参考支持标签的正文段落。部分覆盖更不能直接计为整段证据命中。完整覆盖多个单元也不授权对旧 JEV 分数求和、取最大值或复制某个标签。

## 文本身份检查

为每个原始／投影 chunk 构造两份离线请求：一份采用实际 source 导出文本，另一份使用相同 chunk ID、doc ID、来源顺序及边界的旧规范化导出文本。人工问题、arm、版本、模型／endpoint、预算等保持一致；额外断言 payload 只能在 `candidate.text` 不同，binding 只能在派生的 payload 摘要和 token 数不同。

| 固定文本对照 | 配对数 | 文本相同且当前请求键相同 | 文本变化且请求键变化 |
|---|---:|---:|---:|
| 原始 b0 chunk | 83 | 2 | 81 |
| 规则投影 chunk | 56 | 1 | 55 |
| 合计 | 139 | 3 | 136 |

**3 对键相同不是 3 次历史 JEV 缓存命中，136 对变化也不是历史缓存失效率。** 本轮没有打开历史请求／响应缓存；这些是同一人工问题与当前离线模板下的配对构造。旧 support 客户端还绑定完整批次 payload、task ID、provider 配置和 prompt 版本；仅内容或来源相同不足以证明它与当前请求相同。

对已经构造的请求，预算使用现有 core 的完整证据渲染，包含来源标识头；单独 chunk 的 token 数不能替代它。两文档原始块请求的最大证据数为 297/329 tokens，投影块为 297/328，均不超过固定 1,024。计数仍使用固定本地 BGE tokenizer，包含 special tokens、不截断；这不是服务商用量或费用估算。

若只改变未选中的原文内容，而完整可见问题、文本、角色和请求配置不变，原请求键可以保留；新 receipt 必须记录当前来源版本。该边界由合成测试验证。把无关原文内容硬塞进模型请求键会混淆判断身份与来源归档，因此这里分别记录两者。

## 验证与剩余接入工作

25 项覆盖测试和 33 项适配器测试合计 **58 passed in 0.32s**，包含完整／部分／混合区间、重复文本、额外空白、不可变性、错误来源、篡改快照、同文档版本或 atom 基准冲突、完整渲染预算，以及变化文本拒绝旧人工缓存。测试中的固定响应仅用于验证缓存拒绝行为，不是模型输出。

独立复核对保存的覆盖结果使用区间算术，并直接验证请求 payload、摘要、缓存键、实际文本和来源 receipt，不重跑新算法；具体范围与绑定见[机器结果](results/refiner_jev_source_contract_20261004.json)。公开材料不包含原文、真实问题、原始文档／单元 ID 或凭据。

默认检索流程尚未接入这个适配器。代码检查发现当前 [`load_chunk_records`](../../SLAC/retrieval/dataio/readers.py) 只把部分字段放入 meta，没有保留新 source mode、坐标和跨度字段；[`enrich_chunk_record`](../../SLAC/retrieval/preprocess/anchor_fields.py) 会规范化并改写 `chunk.text`。因此下一步继续零 API：在真实读取／预处理入口保留并验证原文快照，检查检索使用的文本与后续 JEV 判断文本如何明确衔接。不能在默认入口尚未贯通时声称端到端 SLAC×JEV 已完成。
