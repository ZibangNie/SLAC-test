# Activation-only exact control — protocol before execution

This CPU control separates two sources of logical relation-read reduction in the frozen lazy-bounds study: edges whose successor has never been selected, and interval certificates that avoid reading an already active edge. It uses the same 77 development questions, 24 families, 501 empty-cache paths and 23,915 assignment-by-known-subset paths. The second suite includes the first; neither is a probability distribution or an independent sample. No API, new relation label, answer, reference, quality score, GPU or retriever change is involved.

## Structural bound and its scope

The frozen graph contains only eligible directed native-adjacency edges `(A, B)=(i,i+1)`. A pending A becomes active only after B is accepted. Each accepted B has at most one such predecessor. A budget or duplicate-text skip removes a pending candidate without accepting it or activating any new edge. Accepted candidates are never evicted; known and previously requested edges are never requested again. The loop stops as soon as k candidates have been accepted, before reading an edge activated by the kth acceptance.

Consequently any policy that requests only unknown active edges makes at most k−1 new reads, for k≥1. With the fixed k=3, two is a structural upper bound, not evidence for interval certification. If termination occurs with r<k accepted candidates, the last accepted candidate may still activate a queried edge: the bound is then r, not r−1, and r≤k−1. Initial cache entries only reduce new reads. Nonmonotonic whole-pack token counts, candidate gaps, exclusion of candidates labeled no and duplicate-text exclusion do not invalidate the argument. The proof does not extend to arbitrary multi-predecessor graphs, recursive activation, eviction/reselection, repeated reads or reads after termination.

## Fixed comparator

Before every winner-removal step, activation-only requests **all** currently unknown eligible edges with A pending and B already selected, in the original native edge order. It then ranks every pending candidate using exact half-integer priority: yes=2, unknown=1, plus 2 iff its active relation is true. Candidates labeled no are excluded. Ties use original dense rank and then native source order. It removes the winner, skips exact native-text duplicates, and otherwise applies the same whole-pack 1,024-token test. A failed budget test continues to the next iteration. Three accepted units terminate the loop immediately.

The runtime receives only the frozen Core, strict-bool callback, identical initial cache and token-count callback. It receives no full assignment, cube, essential set, lazy request list, quality or reference. Complete assignments are available solely to the external synthetic-oracle harness. Initial cache and relation observations reset for every path; no cross-question deployment schedule is executed.

For every path the comparator must reproduce the audited lazy winner-removal trace, including every skip and proposed token count, and the exact final rendered pack, selected identities, hash and token count. Lazy's queried edge set must be a subset of activation-only's set. Both must avoid initially known edges and repeated requests. The invariant is `lazy_reads <= activation_reads <= min(initially_unknown_eligible, 2)`. Any violation fails the complete run; it is not a negative result to discard.

## Exact token replay and reporting

The directly bound, independently verified lazy events already contain the actual BGE token count of every proposed whole pack and final pack. This control builds a deterministic lookup keyed by sorted unit indices from those records, rejects inconsistent or missing entries, and does not load a tokenizer or infer additive token costs. Identical winner traces justify the lookup coverage. This is exact replay of saved token measurements, **not a serving-latency experiment or a fresh tokenizer benchmark**. Runtime decisions cannot inspect the lazy trace or query set; only the token callback returns the measured integer for the proposed pack.

Both suites retain every path and report the complete histograms and totals for initially unknown eligible edges, activation reads and lazy reads. Report the two differences separately: `eligible − activation` measures activation filtering; `activation − lazy` measures additional interval-certification reduction under this comparator. Report zero differences, maxima, source-qualified requested identities, full-cache zero-read paths, and globally nonessential reads made by **each** method. Essentiality is validation-only metadata obtained after all selection paths, never a runtime shortcut. No confidence interval, expected-read estimate, optimality, provider-call saving, monetary saving or causal quality claim is made.

## Sealing and completion

Preparation validates only complete parent receipts, direct file hashes/inventories, Core projection and the fixed combinatorial denominators. It must not parse path results, build the token cache, run a selector, calculate read savings or inspect essentiality. The plan seals this source, its tests, this protocol, the consumed parent code, complete parent plan/run/audit/independent receipt and root completion marker. Unconsumed ancestor commitments remain inherited and are identified as such; no fresh full ancestor audit is claimed.

A single fixed output directory is exclusive. Run and independent replay audit each have a 300-second cooperative deadline; Root supplies an external 300-second watchdog for execution. Any exception, deadline, changed source, missing path or mismatch leaves no completed summary. Audit reconstructs all 501 and 23,915 comparator paths and all public aggregates from the bound saved parent records; it does not call an API, run the old selector or reload a model. Publication requires the complete audit and independent review. No real preparation or scoring is authorized merely by writing this protocol.
