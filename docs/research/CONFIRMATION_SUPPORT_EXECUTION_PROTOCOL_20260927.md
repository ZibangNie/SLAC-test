# New-budget complete confirmation support execution

This protocol describes code and an explicit future preparation step. It does not accept a pending budget choice, read a key or start a request. Preparation requires a separately supplied positive total USD budget and an absolute timezone-aware deadline. There is no default budget or deadline. The complete support reservation plus the entire five-arm generation upper commitment must fit before preparation succeeds. Generation remains locked and is not executed here. The historical night ledger, its unknown attempt, cap and deadline remain unchanged; this is a new stage, not a refund or a restart of that night.

Use exactly the shared batches and ordered jobs already sealed by the offline budget planner: all questions, both backends, no canary, probe, sample-run substitute, fallback, automatic retry or response repair. One JEV decision is retained for both ordinal and reported-score selection. Keep each raw JEV response and its unnormalized reported yes/no/unknown scores; require the existing reported-score contract. No references or quality metrics enter this stage.

Split the fixed ordered jobs only into transport containers satisfying the existing client's $2, 160-request, 1,600-judgment and eight-million input-allowance limits. A segment does not receive a new global budget. A permanent exclusive registration adjacent to the source budget directory commits the whole support reservation and locks the complete answer reserve. Every request is recorded with its reservation in a flushed append-only event before dispatch. Physical attempts are bounded by the complete frozen job count and derive from one contiguous segment/job sequence, without double-charging its event snapshots. No unknown reservation is refunded. Unattempted support commitment remains visibly committed after failure; there is no automatic release or continuation.

Reuse the original bounded client's exact payload, HTTP, redaction, parse, cost/usage and provider-contract behavior. Its RTF-compatible key extraction runs only in execution; keys and arbitrary exception text never enter logs. Pin the actually observed returned model identities across every segment: `typesafe/jev-1.13-20260917` and `qwen/qwen3.6-plus`. The latter differs from the endpoint metadata's dated slug; do not widen the allowlist on first response. Missing provider metadata retains the inherited request-route-pinned status; a conflicting reported provider stops execution.

Require more than 65 seconds until the explicit deadline both before request preparation and again after durable reservation, before transport. Retain an in-flight unknown if that second gate fails. An absolute watchdog and a 65-second request watchdog exit only this executor process; they never terminate an unrelated process. A timeout, interruption, malformed score/label, model/provider drift, usage overrun or source change halts the complete stage. Preserve known provider cost even on a failed response. A new output directory cannot bypass the budget-family registration. No automatic recovery is provided.

Only complete success publishes the full support judgments and completed summary. A separate audit replays saved raw requests/responses, immutable events, models, usage, reservations and complete task coverage. An explicit incomplete audit reports the preserved attempt prefix and known/unknown cost without quality results or admission to continue. This is mechanical execution accounting, not an exhaustive semantic QA review. Actual answer payload construction and generation admission remain separate future work.

The append-only event is flushed before its mutable ledger snapshot. A process or storage failure exactly between those writes can leave both preserved files inconsistent; the verifier refuses that state rather than repairing or retrying it. Such a crash needs a separately documented forensic review. The incomplete-audit interface therefore does not promise automatic recovery from every possible I/O interruption. Local reservations are admission accounting, not a provider-enforced monetary cap; any reported overrun is retained and stops execution.
